# استقرار سرویس و کنترل اجرای واقعی

`run.py paper` همچنان کاملاً کاغذی است. مسیر مستقل `wallex_lab.cloud` جمع‌کنندهٔ عمومی، پردازشگر حساب واقعی و داشبورد خصوصی را اجرا می‌کند. اولین راه‌اندازی با معاملات خاموش انجام می‌شود؛ نصب یا دیپلوی، مجوز معامله ایجاد نمی‌کند.

## کانتینر

از `Dockerfile.live` استفاده کنید. تصویر پیش‌فرض فقط وابستگی‌های Weekly / late، PyTorch مخصوص CPU، رسم نمودار، MCP و مدیر سازگار با API را نصب می‌کند. مدل نهایی ده‌ارزی همراه مخزن است. مدل‌های حجیم Kronos و Chronos-2 در این حالت دانلود یا بارگذاری نمی‌شوند.

```bash
docker build -f Dockerfile.live -t wallex-live .
docker run --env-file .env -p 8080:8080 -v wallex-data:/data wallex-live
```

حالت منتخب `WALLEX_EXECUTION_PRESET=weekly_council_ten` است: BTC، ETH، SOL، S، XRP، DOGE، ADA، BNB، TRX و LTC همگی با همان Weekly / late سه‌عضوی تحلیل می‌شوند؛ خبر، کلان و مدیر بعد از مدل‌اند. پشتیبانی شش ارز با آموزش ردیف‌های جدید embedding به مدل پایه اضافه شده و پیش‌بینی چهار ارز اولیه دقیقاً حفظ شده است. [روش آموزش و ارزیابی](weekly-ten.md)

هر ده بازار شرط احتمال مطلق TP قبل از SL بالاتر از ۵۵٪ در ۲۴ ساعت، TP دو درصد و SL دو درصد دارند؛ خروج زمانی اجباری نیست. اسکن تکنیکال و حفاظت مستقل از انتظار مدیر و گزارش‌ها اجرا می‌شوند. قیمت، موجودی، هزینه و عمق اجرایی از اتصال احراز‌شدهٔ والکس دریافت می‌شوند؛ کارگر گزارش در این preset دریافت تکراری دفتر سفارش عمومی را اجرا نمی‌کند.

برای ساخت تصویرِ مسیرهای قدیمی چندمدلی، `--build-arg INSTALL_FOUNDATION_MODELS=1` بدهید. آن گزینه وابستگی‌ها و وزن‌های پین‌شده در `config/foundation-models.json` را دریافت و بررسی می‌کند؛ فایل‌های بزرگ داخل Git نیستند. preset و تنظیمات دیسک را هم متناسب با همان آزمایش انتخاب کنید.

با `adaptive_learning=true`، بخش `live_learning.py` نتیجهٔ معاملات کاملاً بسته و قطعیِ همین حساب را می‌آموزد و وزن منابع را به مدیر می‌دهد. هر ده بازار در دفتر یادگیری حضور دارند؛ وزن‌ها بین بازارها مشترک‌اند، آموزش جداگانهٔ ده مدل نیست. بخش قدیمی `adaptive_council.py` همچنان مخصوص آزمایش کاغذی است. [حداقل نمونه، اعتبارسنجی، بازگشت وزن‌ها و محدودیت‌ها](live-learning.md)

ارتقای خودکارِ روش‌های نسخهٔ قدیمی فقط روی تنظیمات شناخته‌شده و با کلید اجرا خاموش انجام می‌شود؛ موجودی، اتصال حساب، سقف سرمایه و تأیید کاربر حفظ می‌شوند. تنظیمات روشن حین boot تغییر نمی‌کنند.

متغیرهای محیطی لازم:

| متغیر | کاربرد |
|---|---|
| `WALLEX_API_KEY` | کلید حساب معاملاتی انتخاب‌شده؛ خواندن موجودی و هزینه در حالت خاموش |
| `WALLEX_DASHBOARD_USER` | نام کاربری داشبورد، پیش‌فرض `admin` |
| `WALLEX_DASHBOARD_PASSWORD` | گذرواژهٔ تصادفی، حداقل ۲۰ نویسه |
| `LLM_PROVIDER` | `openai_compatible` |
| `LLM_BASE_URL` | نشانی HTTPS سرویس سازگار |
| `LLM_MODEL` | مدل دارای ورودی تصویر و خروجی JSON مطابق schema |
| `LLM_API_KEY` | کلید سرویس مدل زبانی |
| `WALLEX_DATA_DIR` | مسیر دیسک پایدار، پیش‌فرض `/data` |
| `PORT` | پورت HTTP، پیش‌فرض `8080` |

کلیدها را در تنظیمات محیطی میزبان قرار دهید؛ فایل محیطی، پاسخ خصوصی، موجودی و دفتر سفارش‌ها وارد Git نمی‌شوند. `LANGSMITH_TRACING=false` در تصویر تنظیم شده است.

## لیارا

یک برنامهٔ Docker و دیسک با نام `data` بسازید. رم ۲ گیگابایت برای شروع این اجرای CPU انتخاب مناسبی است؛ مصرف واقعی و فضای دیسک را پایش کنید. متغیرهای بالا را در تنظیمات برنامه قرار دهید و سپس:

```bash
liara deploy --app YOUR_APP --platform docker --dockerfile Dockerfile.live --liara-json liara.live.json --port 8080
```

`liara.live.json` دیسک `data` را به `/data` متصل می‌کند. در استفادهٔ مستقیم از API انتشار لیارا، همین نگاشت باید در بدنهٔ درخواست انتشار نیز ارسال شود؛ صرف وجود فایل در آرشیو کافی نیست.

فقط `/health` عمومی است. صفحهٔ `/control` و `/api/status` احراز هویت HTTP Basic دارند؛ بیرون از localhost باید پشت HTTPS باز شوند.

پردازشگر دفتر حساب فقط یک نویسنده دارد. اگر پس از انتشار، لاگ `live-runner.lock` نشان دهد نسخهٔ قدیمی هنوز فعال است، فایل قفل را حذف نکنید. پس از توقف صریح معاملات و اطمینان از نبود موقعیت و سفارش مدیریت‌شده، با `liara stop --app YOUR_APP` پایان کارگرهای قدیمی را بررسی کنید و سپس `liara start --app YOUR_APP` را اجرا کنید. تازگی اسکنِ پردازشگر جدید را بررسی کنید؛ وضعیت READY انتشار یا پاسخ سالم صفحه به‌تنهایی اثبات تعویض پردازشگر نیست.

## فعال‌سازی توسط صاحب حساب

1. وارد `/control` شوید و موجودی و شناسهٔ حساب مشاهده‌شده را بررسی کنید.
2. سقف کل سرمایهٔ مجاز را به USDT تعیین کنید.
3. تأیید رفتار واقعی `STOP_LIMIT` را فقط پس از آزمایش خودتان در همان حساب بزنید. این کد، صحت پذیرش و اجرای استاپ را با سفارش واقعی اثبات نکرده است.
4. تأیید معامله با پول واقعی را بزنید و دکمهٔ «فعال‌کردن معاملات واقعی» را فشار دهید.

پیش از ثبت تغییر، سرور تازگی مشاهدهٔ حساب، شناسهٔ حساب، سقف سرمایه و محدودیت‌های ریسک را بررسی می‌کند. تغییر تنظیمات اتمی است و اقدام کاربر ثبت می‌شود. شروع اولیه با `enabled=false`، حساب متصل‌نشده، سقف سرمایهٔ خالی و استاپ تأییدنشده است.

فعال‌سازی، ورود فوری ایجاد نمی‌کند. در حالت منتخب، هر ده ارز باید از احتمال مطلق TP-first بالاتر از ۵۵٪ عبور کنند؛ سپس مدیر و درگاه هزینه، اندازه و ریسک را بررسی می‌کنند. خروج زمانی اجباری وجود ندارد.

تعداد ده بازار سقف چهار موقعیت هم‌زمان یا محدودیت‌های سرمایه و ریسک را افزایش نمی‌دهد. در preset منتخب، فهرست‌های `probability_symbols`، `legacy_technical_symbols` و `llm_chart_symbols` خالی‌اند و مدل اصلی ده‌ارزی است. بازده تاریخی ۱٫۳۴۳٪ همچنان متعلق به آزمایش چهارارزی قبلی است.

در ارتقای دیسک قدیمی، فقط تنظیم خاموشِ شناخته‌شدهٔ چهارارزی با هش مدل قبلی به فهرست ده‌ارزی و مسیر تحلیل ترکیبی منتقل می‌شود. اتصال حساب، سقف سرمایه، تأیید استاپ و محدودیت‌های کاربر حفظ می‌شوند؛ تنظیم روشن یا مدل سفارشی خودکار عوض نمی‌شود. تغییر فهرست بعدی توسط اپراتور در بازراه‌اندازی پس گرفته نمی‌شود.

در حالت خاموش، مشاهدهٔ حساب و پیش‌بینی تکنیکال انجام می‌شود؛ تصمیم خصوصی حساب به LLM ارسال نمی‌شود و نیت سفارش ساخته نمی‌شود. گزارش‌های عمومی خبر و کلان همچنان می‌توانند از LLM استفاده کنند. پس از فعال‌سازی، مدیر موجودی، موقعیت‌ها، نمودار و گزارش‌ها را برای تصمیم دریافت می‌کند؛ کلید API وارد ورودی مدل نمی‌شود.

## داده و نگه‌داری

### حالت اختیاری چهار بازار بدون مدیر زبانی

برای اجرای مستقل Weekly / late روی BTC، ETH، SOL و S، متغیر محیطی
`WALLEX_EXECUTION_PRESET=weekly_model_only` را تنظیم کنید. تغییر حالت فقط وقتی
`enabled=false` است انجام می‌شود و اتصال حساب، سقف سرمایه و حدود ریسک کاربر حفظ می‌شوند.
پیش از تغییر فهرست، نبود موقعیت و سفارش مدیریت‌شده را بررسی کنید؛ بازارِ موقعیت باز نباید از پیکربندی حذف شود.

در این حالت فقط مدل سه‌عضوی قبلی اجرا می‌شود: TP دو درصد، SL دو درصد، احتمال مطلق
TP قبل از SL در ۲۴ ساعت **بیشتر از ۵۵ درصد**، بدون خروج زمانی. ورود پیش از ارسال
با مظنهٔ تازه دوباره امتیازدهی می‌شود؛ درگاه موجودی، کارمزد واقعی، اسپرد، اندازه و ریسک
و استاپ بومی را همانند قبل بررسی می‌کند. نگهداری فقط با حدهای مالکیت‌شده انجام می‌شود؛
هیچ خروج زودهنگام مدیر وجود ندارد.

کارگر خبر/کلان و درخواست‌های BoxAPI در این حالت اجرا نمی‌شوند و گزارش قدیمی در تصمیم
دخالت ندارد. یادگیری وزن منابع غیرفعال است چون مدیر و ترکیب منابعی در این آزمایش نیست؛
دفتر سفارش و معاملات همچنان روی دیسک ذخیره می‌شوند. بازراه‌اندازی حساب را خودکار فعال نمی‌کند.
این همان تنظیم عددی آزمایش چهارارزی با بازده تاریخی حدود ۱٫۳۴٪ است؛ اجرای زنده،
قیمت‌های قابل معامله و تاریخچهٔ جانشین، تضمین تکرار آن نتیجه نیستند.

بررسی بدون شبکه: `python checks/check_weekly_model_only.py`؛ محیط باید وابستگی‌های مدل را داشته باشد.

قیمت اجرایی، دفتر سفارش، موجودی و کارمزد از والکس‌اند. تنظیم همراه برای تاریخچهٔ پیوسته، KuCoin و برای SOL، XRP و LTC، MEXC را به کار می‌گیرد. قیمت کل پنجره با نسبت کندل هم‌زمان والکس تنظیم می‌شود و حجم متعلق به منبع تاریخچه باقی می‌ماند. ارزیابی تاریخی مدل جای کالیبراسیون روی دادهٔ زندهٔ این بازارها را نمی‌گیرد. `history_mode=native` فقط کندل‌های واقعی والکس را می‌پذیرد و شکاف را با دادهٔ ساختگی پر نمی‌کند.

گاهی پاسخ موفق والکس پیش از انتشار آخرین کندل برمی‌گردد. دریافت کندل مبنا حداکثر سه بار با فاصلهٔ ۸ ثانیه، برای همان دقیقه تکرار می‌شود. اگر هنوز منتشر نشده باشد، وضعیت `data_pending` با دلیل روشن ثبت و دور بعد ۱۵ ثانیه بعد شروع می‌شود. زمان تحلیل عقب برده نمی‌شود و کندل جایگزین ساخته نمی‌شود. خطاهای دیگر نیز کد و محل شکست امن دارند؛ متن خام خطای سرویس‌ها در داشبورد نمایش داده نمی‌شود.

تنظیم فعال‌سازی و دفتر SQLite روی `/data` می‌مانند؛ اگر کاربر قبلاً فعال کرده باشد، بازراه‌اندازی همان وضعیت ذخیره‌شده را حفظ می‌کند. خرید آماده ولی ارسال‌نشده در شکست یا بازراه‌اندازی کنار گذاشته می‌شود و تحلیل تازه می‌خواهد. نتیجهٔ نامعلوم سفارش حفظ و تطبیق داده می‌شود و کورکورانه تکرار نمی‌شود.

دکمهٔ توقف، ورود و تصمیم خودکار را متوقف می‌کند؛ موقعیت را نمی‌فروشد و سفارش حفاظتی بومی قبلی را لغو نمی‌کند. پیگیری نرم‌افزاری TP هم در حالت خاموش متوقف است. در وضعیت اضطراری، `WALLEX_FORCE_DISABLE=true` را روی میزبان تنظیم و سرویس را بازراه‌اندازی کنید. برای فعال‌سازی بعدی این متغیر را حذف یا false کنید.

حفاظت مستقل از دریافت تاریخچه و انتظار LLM اجرا می‌شود. توقف بومی از نوع STOP_LIMIT است و تضمین پُرشدن در شکاف قیمت ندارد؛ زمان ثابت برای خروج نیز تضمین نمی‌شود.

```bash
python checks/check_cloud.py

```

این بررسی‌ها از حساب و صرافی ساختگی استفاده می‌کنند. بررسی درگاه شامل عدم ارسال در حالت خاموش، ریسک، سفارش نامعلوم و حفاظت است؛ آزمون وب شامل احراز هویت، CSRF، تازگی حساب و فعال‌سازی صریح کاربر است. هیچ‌کدام سودآوری یا عملکرد استاپ واقعی را اثبات نمی‌کنند.
